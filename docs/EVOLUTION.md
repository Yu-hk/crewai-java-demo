# 演进记录：P0 → P3.5

README 描述的是**最终形态**——每个模块现在长什么样、为什么这么设计。
这份文档记录的是**长成这个形态的过程**：每一步由什么问题触发、当时怎么判断、做完之后又暴露了什么。

两者的区别很实际。README 里的设计理由都是"事后看来正确"的，
而真实推进时并不知道下一个坑在哪。记录顺序，是为了让后来者能判断
"我现在卡住的地方，是不是别人也在这里卡过"。

> 为什么不直接看 git 提交历史：分层是按包组织的，`core/` 里同时装着 P0 的
> `Guardrails`/`ContextBudget` 与 P1 的 `RunStore`/`CrewListener`，且 `Task`、`Crew`
> 在两个阶段都引用它们。按阶段切出来的中间提交**无法编译**，`git bisect` 会直接失效。
> 所以仓库是单次快照，演进过程用文档补。这是取舍，不是遗漏。

## 一、时间线总览

| 阶段 | 触发问题（可观测） | 主要交付 | 收敛判据 |
|---|---|---|---|
| **P0** 契约与运行时 | 三步流程能跑通，但产出是散文，程序无法消费 | 结构化输出、原生 function calling、上下文预算、Guardrails、重试限流 | 9.1 的产出能被代码校验并通过 |
| **P1** 工程化 | 130 秒链路在第三步失败，只能全量重跑，且重跑结果不一致 | 断点续跑、事件钩子、DAG 桥接 | 中断 → 续跑 → 幂等重放三步演示走通（9.5） |
| **P2** 协议与生态 | 每接一个外部能力都要写适配类 + 重写 Schema + 重新编译 | MCP stdio 客户端、自带 demo 服务端 | 第三方 `server-everything` 五项协议验证通过（9.8） |
| **P3** 经验与知识 | 跨运行的经验无处沉淀；文档只能全量塞进提示词 | 语义记忆、知识库与分块 | 跨进程召回生效 + 常驻注入生效（9.9、9.10） |
| **P3.5** 工具可见性 | 工具从"自己写的 1 个"变成"服务端给的 4 个、13 个" | `ToolSet` + 任务级绑定 | 同一流程内两个任务工具来源不同且不互相污染（9.12） |

一句概括这五个阶段的关系：**下一阶段的需求，通常由上一阶段的成功造成**。
P3.5 最典型——它不在任何初始计划里，是 P2 把工具数量从自己可控变成服务端决定之后，
`Agent.tools` 这个字段才第一次成为瓶颈。

## 二、P0：让产出能被代码消费

### 症状

第一版能跑：`Agent` 拼四段提示词，`Task` 带描述与期望输出，`Crew` 顺序执行，纯文本协议。
流程是通的，但下游接不住——第三步拿到的是"一段看起来不错的分析"，要取其中某个数字，
只能用正则去捞。

### 判断

这不是"提示词写得不够详细"的问题。`expectedOutput` 是一句话，`outputType` 是一套可校验的结构；
前者靠模型自觉，后者靠代码兜底。**凡是产出要被程序消费，就必须有契约。**
于是 P0 的第一件事是 `schema/Structure`：反射生成 JSON Schema、绑定回 POJO、校验失败把具体错误回灌。

### 交付（五项，都有必要）

| 能力 | 对应 CrewAI | 补它的直接原因 |
|---|---|---|
| 结构化输出 | `output_pydantic` | 散文无法被下游消费 |
| 原生 function calling | `tools=[...]` | 文本协议全靠模型输出 `[TOOL]` 约定格式，漏一次就退化成编造 |
| 上下文预算 | `respect_context_window` | 硬编码丢历史，中文场景下按字符算预算偏差一倍以上 |
| Guardrails | `guardrail=` | 格式校验只能保证形状，保证不了内容 |
| 重试与限流 | 重试退避 | 一次 429 就让整条链路失败，本地跑也会把显卡打满 |

### 这一步暴露的三个坑

**结构化输出与工具调用互斥**（坑 1）：把"输出 JSON"和"用 calculator 算数"写在一个 prompt 里，
三次尝试一次都没调工具，模型直接编了数字。JSON 是强格式约束，模型为满足它会跳过中间步骤。

**修好坑 1 之后坑更深**（坑 2）：结构化一次通过，但 `increasePercent = 100`（正确答案 500）。
**格式合法把错误的可见度降低了**——它把"一眼假"变成了"看起来真"。这才是需要语义校验的真正理由，
而不是"校验器越多越好"。

**校验标准定得比模型能力高，等价于必然降级放行**（坑 3）：要求"恰好 2 条"时 7B 稳定给 3 条，
耗尽重试后 106 秒才放行。放宽成 `>= 2` 一次通过。

### 收敛判据

不是"代码写完了"，而是 9.1 那次实跑里，结构化校验通过、`parsed` 里能直接读出
`judgments` 与 `increasePercent` 两个字段、且数值与工具计算结果一致。
在这之前，P0 都算没做完。

## 三、P1：让链路可以失败

### 症状

一次完整运行约 130 秒。第三步失败 = 前两步白跑，且重跑结果不一定一致——
前两步产出变了，第三步面对的输入也变了。更直接的问题是可观测性：
进度、成本、失败归因全是硬编码在 `Crew` 里的 `System.out.println`，
想接一个 web 进度条就得动核心类。

### 判断

P0 把"成功路径"做对了，P1 要处理的是"失败路径"和"被嵌入其他系统的路径"。
两者的共同点是：**它们都不能靠改业务代码解决**，必须在架构上留出接缝。
所以 P1 的三项交付（`RunStore`、`CrewListener`、`CrewNode`）本质是三个接缝，不是三个功能。

### 交付

| 接缝 | 交付物 | 关键决策 |
|---|---|---|
| 时间（进程重启） | `RunStore` + `RunState` + `FileRunStore` | 只存原始文本，恢复时用 `outputType` 重新绑定 |
| 可观测性 | `CrewListener`（15 事件）+ `ConsoleListener` + `MetricsListener` | 内核零打印，全部走事件 |
| 嵌入宿主 | `CrewNode` + `SimpleDag` | 只做桥接，不重写 Flow 引擎 |

三个决策里最值得记的是第一个：**存序列化后的对象更"完整"，但更脆弱**——改了字段类型，
旧存档就再也读不回来。存原始文本 + 重新绑定，代价是一次本地解析，换来的是存档与 POJO 结构解耦。

### 这一步暴露的三个坑

**"有存档就复用"是危险的语义**（坑 4）：它看起来是一次正常成功，实际拿的是上一版 prompt 的产出。
必须校验任务标签与输入变量，宁可抛异常要求换 `runId`。

**中断路径必须自己落盘 `FAILED`**（坑 5）：不写状态，下次启动看到的是 `RUNNING`，
无法区分"还在跑"和"上次挂了"。`CrewException` 带 `completedSteps` 同理——
只说"失败了"的异常没法用来决策。

**耗时口径要提前定**（坑 6）：`CrewOutput.millis` 若包含复用任务的历史耗时，
"续跑省了多少时间"就看不出来——续跑会显示 40 秒而不是 0 秒。

### 收敛判据

9.5 的三步演示全部走通：中断时 `status=FAILED` 且 `completed` 只有 1 条；
续跑后变 `DONE` 且 3 条；第三次全部复用、0 调用 0 秒。
同时 31 项离线断言覆盖了存档往返、幂等重放、三道一致性校验、拓扑排序、环检测。

**离线断言的引入是 P1 的隐性成果**。P0 阶段只有实跑，每次验证要等 46 秒以上且受采样随机性影响；
P1 开始用假 `LlmClient` 跑真实 `Crew`，覆盖度上去了，耗时降到毫秒级。

## 四、P2：让能力从协议里来

### 症状

接第一个外部能力（读文件）时写了适配类；接第二个（查时间）又写一遍。
模式完全重复：写类 → 写 Schema → 编译 → 重启。而 Schema 的拥有者其实是服务端。

### 判断

这是"适配层该由谁来写"的问题。答案是由协议对端写，客户端只做透传。
于是决定实现 MCP 客户端——**只做 stdio，不做 SSE / streamable HTTP**。

这个取舍值得展开。省事不是理由，真正的理由是：SSE 与 HTTP 要处理会话 ID、断线重连、OAuth 回调，
这些与"多智能体协作"没有关系；而 stdio 是唯一能做到"一条消息进、一条消息出"的传输，
最适合把协议本身看清楚。传输层做成接口，接远程时新增一个实现即可，`McpClient` 不用改。

### 交付

11 个类，其中 `DemoMcpServer` 是刻意的投资：在**没有 Node、没有网络**的环境里也能验收协议层，
同时它自己就是一个"故意不合规"的样本（`echo.debug` 名字带点），用来验证客户端名称合法化确实生效。

### 这一步暴露的三个坑

**整数被写成浮点，跨协议才暴露**（坑 7）：`limit=200.0`。根因在 JSON 层——解析阶段所有数字
都变成 `Double`，原样输出时 `200` 就成了 `200.0`。对声明 `integer` 的参数，严格校验的服务端
（zod 之类）会直接拒绝整个调用。

这条坑的价值超出 MCP 本身：**跨进程协议会把本地"能跑"的东西照出原形**。反射绑定对 `200.0`
是宽容的，本地工具永远不会暴露这个问题。

**反向请求不回复 = 静默挂起**（坑 8）：服务端发 `roots/list` 后等回应，客户端把"带 id 的入站请求"
当不认识的消息丢掉，服务端永久卡住，而客户端看到的是"工具调用超时"——**报错信息指向错误的一方**。
这类 bug 的特征是责任方无日志，必须显式回 `-32601`。

**工具挂上去 ≠ 模型会用**（坑 9）：挂官方 `server-everything` 的 5 个工具，模型一次都没调；
换成 `word_count`（正好解决"200 字上限"这个它当下的困境）立刻被调用。
选 MCP 服务端时，"有哪些工具"远不如"这些工具是否咬合当前任务"重要。

### 收敛判据

9.8 里对同一个第三方服务端连续做五项验证：`echo` 中文往返、图片内容块、参数校验失败回灌、
2 秒长任务的 progress 通知不错位、反向请求得到响应。全部通过才算 P2 完成。

## 五、P3：把经验与文档变成可检索的东西

### 症状

两个具体问题：跨运行的经验无法沉淀（同一类错误反复踩）；40 KB 的 README 想用只能全量塞进提示词。

### 判断

先要划清它与 `ContextBudget` 的边界，否则会做重复：

```
全量历史 ──[Memory：语义检索]──> 相关的若干条 ──[ContextBudget：压缩]──> 装进窗口
             选择（丢弃无关）                    压缩（保留要点）
```

**顺序不能反**。先压缩再检索，等于先把可能要用的信息压掉了再去捞；而且压缩要花一次模型调用，
对本来就不该进来的内容花这次调用是纯浪费。

一句话区分：`ContextBudget` 解决"窗口内塞不下"，`Memory` 解决"这条信息根本不该在这个任务里出现"。

### 交付

14 个类。三个设计决定撑起了整个模块：

1. **一个存储 + 一个作用域枚举**，而不是 CrewAI 的四个存储类——四套检索路径换来的区分度，
   用一个枚举加"按作用域变化的半衰期"就能表达，检索逻辑只保留一条。
2. **`Embedder.baseline()` 由实现自己声明**——阈值不能跨模型复用。同一套"0.5 算相关"的规则，
   用在 bge-m3 上一个都召不回，用在哈希实现上全是噪声。
3. **`Importance` 用启发式，不做 LLM 打分**——每写一条多一次调用，7B 上同一段文本两三次
   给出 4/7/5 分，等于给检索注入随机噪声。

### 这一步暴露的五个坑（P3 的坑最密，也最值得看）

**存的是产出，检索键却是任务描述**（坑 10）：第一版把记忆写成"任务标签 + 产出"，
下一轮同样的任务几乎召不回自己上次的结果。一个说"分析成本"，另一个讲"调试链路变长"，
在语义空间里相距很远。改成"任务描述 + 产出"后，召回分从召不回变成 0.89。
**检索键与存储键必须是同一个东西**——这是纯粹的实现纪律，与算法无关。

**绝对阈值在 bge-m3 上不可用**（坑 11）：按直觉写"相似度 < 0.5 算无关"，
实测 45 对互不相关的中文短句，最高能到 0.538，而真正弱相关的只有 0.56，两个区间重叠。
这不是阈值调得好不好的问题，是**这条路本身走不通**。改用相对截断（保留最高分的 72% 以内），
绝对阈值只用于判断"整批候选是不是全是噪声"。

**噪声地板会系统性误杀高价值记忆**（坑 12）：加上 0.54 地板后，三条精心写的长期记忆
（相关性 0.326 / 0.371 / 0.443）全部被挡。**价值最高的信息往往字面相关性最低**——
两条输出规范与任务主题的相似度比随机无关还低，却对每份产出都有约束力。
解法是两条独立通道：常驻注入（无条件生效）与重要性豁免（高价值低相关）。

**被切断的代码块，检索看不出问题**（坑 13）：76 块里 27 块带未闭合围栏，
但它们仍然正常嵌入、正常命中、正常注入 prompt——**检索质量指标完全正常**，
只有把 prompt 打印出来才看得见。

**记忆会让模型抄自己上一轮的答案**（坑 14）：召回分 0.89，第 1 步产出与上一轮逐字相同。
这既是记忆生效的证据，也是副作用——SHORT_TERM 给了模型一份标准答案，它不再重新推理。
结论是划清界限：短期记忆只服务同一次会话内的连贯性，跨运行要沉淀的应当是结论与教训。

### 收敛判据

9.9 跨进程召回（分数排序合理）+ 9.10 常驻注入与重要性豁免同时生效
（三条相关性全部低于地板、却全部被注入）+ 9.11 知识库索引 66 块且检索命中准确。
三者都成立，P3 才关账。

## 六、P3.5：工具可见性属于任务

### 症状

P2 之后工具数量由服务端决定。`server-everything` 有 13 个工具，全挂到 `Agent` 上，
光是描述就占掉上千 token——而 9.8 的实测结论是模型一个都不会用。
另有两种情况：同一 Agent 承担多任务时各阶段需要的工具不同；"工具来源"（运维概念）
与"工具可见性"（设计概念）被混在同一个 `Agent.tools` 字段里。

### 判断

CrewAI 里工具只能挂 `Agent`，`Task` 没有 `tools` 参数。这在"一个 Agent 只做一件事"时没问题，
一旦上面三种情况出现就难受。而为了工具差异拆成两个 Agent，人设就要维护两份——
**人设恰恰最不该分裂**。

### 交付

`tool/ToolSet`（不可变命名集合）+ `Task.toolset(...)` + `Agent.execute(prompt, events, ToolRegistry)`
运行期重载。

这次交付的重点不在新类，而在**改了一个签名**：工具集必须是 `execute(...)` 的运行期参数，
不能写回 `Agent` 字段。原因很具体——同一个 Agent 被多个任务共用时，
任务 A 收窄过的工具集会漏给任务 B，而且**不会报错**，只表现为"模型有时不调工具"。

连带的硬约束：工具出现在五个地方（系统提示词清单 / `tools[]` 声明 / 调用分发 /
"先调工具再填 JSON"的措辞 / 绑定日志），必须**五处同源**。只改一处，模型就会去调一个
没有声明的工具，收到"未知工具"，再换个名字重试——白烧两轮。

### 这一步暴露的两个坑

**用 token 数论证工具集的价值，会得出"不值得做"的结论**（坑 15）：4 个工具 185 tok、
1 个工具 64 tok，省 65% 听起来不错，但那只是工具清单的 65%，占一次请求输入的 3%。
更危险的是 A/B 两轮输入差 1,505 tok，其中约 1,400 来自 A 那轮多出的一次重试——
差一点就把重试的运气算成工具集的功劳。

这条坑的普遍意义大于结论本身：**小样本对比里，重试次数和采样随机性会轻易盖过真实效应量，
必须把变量拆开单独量**。真正的论据不是 token，而是 9.8 里 13 个工具一个都没被调用。

**工具集一旦写回 Agent 字段就会串味**（坑 16）：见上文。这条坑的可复现特征是"不报错、
只是偶发不调工具"，属于最难查的一类。

### 收敛判据

9.12 的 B 组：`writer` 的工具来自 `mcp:demo-tools`，`analyst` 的来自 `local`——
**同一个流程里两个任务工具来源不同**，这在按 Agent 绑定下做不到。
加上 27 项离线断言覆盖"上一个任务的收窄不泄漏给下一个任务"。

## 七、验证资产随阶段增长

| 阶段 | 断言数 | 覆盖重点 | 依赖模型 |
|---|---|---|---|
| P0 | 0 | 只有实跑对比 | 是 |
| P1 | +31 | 存档往返、幂等重放、一致性校验、拓扑排序、环检测 | 否 |
| P2 | +28 | 握手、翻页、通知插入、响应乱序、反向请求、名称合法化 | 否 |
| P3 | +54 | 向量编解码、去重、衰减曲线、相对截断、分块与围栏保护 | 否 |
| P3.5 | +27 | 集合运算、五处同源、空集不回退、收窄不泄漏 | 否 |
| **合计** | **140** | 0.3 秒跑完 | 否 |

P0 阶段没有断言，是这份演进里最明显的一处欠账。P1 之后每一层都先写断言再实跑，
回归成本从"46 秒一次且结果不稳定"降到"0.3 秒且确定"。

前 54 项用 `HashingEmbedder` 而不是 bge-m3，理由不是省事：记忆层绝大多数 bug
（打分算错、去重阈值、作用域过滤、存档往返）与语义质量无关，用真模型测只会每轮多等十几秒，
还引入"模型今天答得不一样"的噪声。语义质量的结论另用 9.9–9.11 的实跑数据支撑。

## 八、事后看，有三处顺序可以更好

标注为"事后判断"，因为当时并无这些信息。

**一，阈值标定应该前置到 P3 第一天。** 45 对无关中文短句的余弦实验是在踩了坑 11 之后才做的。
如果先做这个标定，会直接得出"绝对阈值在 bge-m3 上不可用"，省掉一整轮返工，
而且 `Embedder.baseline()` 这个设计会更早出现。

**二，离线断言应该从 P0 就开始。** P0 的五项能力全靠实跑验证，每次 46 秒起且结果受采样影响。
P1 建了 `SelfTest` 之后才意识到：P0 的上下文预算与重试逻辑其实完全可以用假客户端断言，
当时花在"重跑一遍看看"上的时间远超写断言的成本。

**三，`ToolSet` 的接口预留可以在 P2 之前。** P2 引入 MCP 时，`Tool` 已经加了
`parametersJson()` 与 `aliases()`；如果当时顺手把"工具从哪来"与"任务能看见什么"分开建模，
P3.5 就不需要改动 `Agent.execute` 的签名。这是一次 API 变更，虽然发生得早、代价不大。

## 九、三个反复出现的模式

从 16 个坑里能看出三种重复出现的结构，它们比单个坑的修法更值得记住。

**一，每次跨边界，都会暴露一批本地看不出的 bug。**
进程边界 → 坑 7（整数写成浮点）、坑 8（反向请求挂起）；时间边界 → 坑 4（旧存档静默复用）；
语义边界 → 坑 11（绝对阈值）、坑 13（切断的代码块）。
共同点：本地"能跑"不代表契约正确，而跨边界是唯一能照出原形的镜子。

**二，每次引入"熵"（自主性、语义、外部工具），都需要一条不经过熵的通道。**
记忆带来语义检索 → 需要常驻注入与重要性豁免（不经过检索）；
工具从服务端来 → 需要 `ToolSet.empty()`（显式不给工具，不回退）；
Agent 自主调工具 → 需要确定性代码节点兜底（`compose` 补标题而不是靠提示词反复强调）。
**自主性每增加一分，与之配对的确定性就必须同步增加一分**，否则系统会漂。

**三，每一个"看起来能省成本"的优化，都必须单独量。**
坑 15 是最典型的反面教材：把重试的运气算成工具集的功劳，差点得出"不值得做"的结论。
同类还有坑 3——校验标准过严带来的不是"更严格"，而是 106 秒后降级放行。

## 十、当前的边界

README 第十一节列了未对齐项。这里补充一句判断标准：
**是否继续推进，取决于它是否服务于"把机制看清楚"这个目标**，而不是"是否与 CrewAI 功能对齐"。

按这个标准，并行任务的优先级低——单卡 Ollama 上收益有限，真正有意义的是
"便宜模型跑草稿、贵模型评审"，那是模型编排问题而非并发问题；
向量索引同样低——千条量级全量扫描约 2 ms，十万条以上才需要 ANN。

而 MCP 远程传输优先级较高：传输层已经是接口，新增 SSE 实现能验证"接口抽象是否真的够用"——
**接口设计得对不对，只有第二个实现能证明**。这和 `Embedder` 有两个实现的理由一样。
